## Findings

### 1. Host checks compile extracted kernel code but model important integration boundaries

Nonblocking for this isolated test. Proven by reading `plans/freeform/tests/exec_env_check.py:95`, `:118`, `:138`, `:157`, `:230`, and `:272`.

The check really cuts out and compiles `sweet_ui_exec_path`, the new helpers, the full `exec_extract_strings`, and the new caller fragment around sugid. It does not compile the real `exec_handle_sugid` into the host executable. The stub explicitly implements the proposed output argument and sets the requested final flags. Thus a broken output assignment in the real function could pass these behavioral tests. I independently read that real assignment and its control flow.

Path reconstruction, process identity, fd locks, user copying, boot-arg parsing and arm64e enablement are stubs. A wrong real flag value, a different VFS context process, a cache alias, a race, or the real parser's numeric handling would escape the model. The model defines `VN_GETPATH_NO_PROCROOT` as 0x8, agreeing with the connected source, and I followed its real implementation separately.

The printed PTRS are offsets derived by walking argv and env strings. They are not the kernel's copied-out vector. They omit NULL slots, apple strings, stack addresses, pointer encoding and copyout failures. A bug in real copyout could remain invisible even when this comparison passes. I read `K/bsd/kern/kern_exec.c:6574` through its descriptor and pointer-writing loops. Renaming a fixed-width prefix preserves the inputs those loops consume.

`run` compares stdout while ignoring subprocess status and stderr. If both executables crashed identically, the matrix could count their empty output as equal. It also starts a new executable for every case, so it cannot exercise concurrent first use of the static enable cache. These are limits on the byte-for-byte claim, not a demonstrated off-mode regression. My additional negative checks explicitly required successful child status and `RC 0`.

### 2. The late finder checks the saved path, not the full vnode match

Nonblocking for this test. Proven by reading `P:113` and running an additional host case.

Automatic injection requires both path checks and the chroot checks at `P:91`. The late finder at `P:113` only requires the saved string `/Applications/Freeform.app/Freeform`. Concrete case: that path resolves to `/private/other`, and explicit `sweetexecenv=Freeform:DYLD_INSERT_LIBRARIES=/usr/local/lib/bgmtl/bgmtl-inject.dylib` supplies the exact app value. A restricted signature causes the late finder to rename this explicitly supplied variable even though automatic matching failed.

The author's narrower Notes claim is fixed. A restricted Notes exec with that same explicit sweetexecenv value retains it. The remaining case changes an explicit experimental override while the feature is on and fails toward disabling injection. It does not automatically inject another executable or affect arg-off behavior. Describing the late check as using the full exact-vnode predicate would overstate its scope.

### 3. A broken library can kill Freeform before its watchdog exists

Nonblocking for an isolated experimental boot. Proven placement by reading `P:42`, `P:197`, and `plans/freeform/next-ff/Chlorophyll/inject/bgmtl_inject.m:546`, `:591`, `:618`. Exact loader outcomes are inferred, not phone-tested.

Concrete case: dyld accepts the injected image, then a dependency, fixup, initializer or device-registration operation fails. Freeform can die before the watchdog is created at line 618. The kill-switch and dead-man code cannot prevent loader failures that occur before the constructor reaches those checks. The kernel has no retry or stock-launch fallback for this library.

Direct new automatic exposure is Freeform only. Exact inherited app, combined and denied values are stripped on child exec while this feature is on. That does not isolate GPU effects. As documented in `analysis/freeform.md` under risk to the compositor, clients share GPU resources, and a bad dispatch can stall the compositor or trigger recovery affecting other clients. Wild GPU writes are a further inferred cross-client risk. This audit did not establish hardware containment or verify the injected binary against all of its source.

A combined refusal also disables sweetsb in Freeform for that exec. This is deliberate at `P:148`, since the whole name is renamed. Other UI apps keep the baseline sweetsb behavior.

## Verification of the fixes

### Chroot, containers and symlinks

Closed by source reading and host negatives. `P:78` reads `fd_rdir` under each process's fd lock and refuses a NULL process. `P:99` tests both `current_proc()` and `vfs_context_proc(imgp->ip_vfs_context)`. The log contains `refused for ...: a chroot`.

`K/bsd/vfs/kpi_vfs.c:1468` derives the context proc from its thread. Spawn installs the new thread into that context at `K/bsd/kern/kern_exec.c:4921` before activation. Ordinary exec installs it at `:6168`. Thus the second check reaches the target process rather than merely repeating the caller check. The caller-only and target-only chroot host cases both refuse.

`P:104` uses `vn_getpath_ext` with a correctly typed size_t length and `VN_GETPATH_NO_PROCROOT`. `K/bsd/vfs/vfs_subr.c:3695` translates this into `BUILDPATH_NO_PROCROOT`, and `K/bsd/vfs/vfs_cache.c:539` then ignores the process root. An executable at `/private/var/trial/Applications/Freeform.app/Freeform` cannot pass the machine-root path comparison. Longer paths and path-builder errors fail closed.

An app sandbox container is not necessarily a chroot. A launcher with an ordinary sandbox that executes the actual accepted machine path may receive injection into that Freeform image. A Freeform-shaped executable inside its container fails the vnode path comparison. A differently spelled symlink to real Freeform fails the saved path check. The exact accepted path symlinked to a differently named target fails the vnode check.

This is namespace matching, not binary authentication. Default firmlink presentation, hard-link cache names, concurrent renames and filesystem aliases remain properties of the path builder. Replacing the file at the accepted system location changes the accepted artifact. I found no new practical wrong-vnode case from the patch under the stated trial setup. No live namespace or container behavior was exercised.

### Off-mode equivalence

Closed by reading `P:49`, `:65`, `:115`, `:169`, `:182`, and `:218`, plus the retained host matrix.

The parser accepts only exact `Freeform`. Unset, Notes, 0, lowercase freeform and the other tested rejected strings produce no new printf. New inherited-value stripping, late scanning, sweetexecenv duplicate bookkeeping and the MAC output store are gated. With the gate off, `sweet_app` is false and the append string is exactly baseline `sweet_insert`, with the same length and accounting. The former unconditional duplicate fix is gone.

The literal statement that every added line is inert is too strong. The kernel still calls the enable helper, parses and caches the boot arg, initializes new locals and calculates the existing string length. The supported conclusion is unchanged exec environment, counters, decisions and added console output. It is not identical machine code or zero overhead.

Here, a refused boot-arg value means the gate is off. A chroot or credential refusal with exact `sweetappmetal=Freeform` is enabled-mode behavior and can log or strip values, as designed.

### One MAC decision and every sugid exit

Closed by source reading. A search of the kernel C and header files found one actual caller, one declaration and one definition of `exec_handle_sugid`. All three are updated by `P:11`, `:22`, and `:209`.

The separate query is removed. Under CONFIG_MACF, `P:218` stores the result of the original query, before the function branches on that same `mac_transition`. The backward jump to `handle_mac_transition` stays below the query and does not query again. I read the complete function at baseline `K/bsd/kern/kern_exec.c:7705` through its sole final `return error`. There are no early returns bypassing this store.

The caller initializes the output to zero. With CONFIG_MACF disabled, the function ignores the pointer and the zero remains correct. With the feature off, the pointer is not written. On a sugid error the caller skips the new check and follows the existing failed-exec path. There is no successful release through that error branch.

### Credentials and code-signing order

Closed by source reading and stub-timed host checks. Signature flags enter `ip_csflags` at `K/bsd/kern/kern_exec.c:2199`, with inheritance through `:2226`. Real MAC credential labeling can update that same field at `:7829`. The new refusal follows sugid and reads `imgp->ip_csflags`, not the still-old proc code-signing flags. Publication occurs later at `:8760` in `process_signature`.

P_SUGID is checked after sugid sets or clears it. All listed set-id mode and signature masks reach refusal. The tested hardened-runtime and set-id transitions occurred inside the host sugid call, and my additional cases covered each listed mask at both pointer widths. These prove the check's response to those final inputs. Real policy and credential transitions were established by reading, not by running kernel code.

The check precedes apple-string construction and copyout at `:2572`. Later signature rejection fails exec rather than making an unchecked process runnable. The installed app's claimed absence of a `__RESTRICT` segment was not independently re-established from a root image in this audit.

Spawn and ordinary exec use the same activator and the same target proc for sugid and the late check. This build's compiler macro dump has CONFIG_MACF=1 and no CONFIG_VFORK definition. `K/bsd/kern/syscalls.master:120` selects nosys without CONFIG_VFORK, and the activator has `vfexec=0` at `:1960`. I do not claim separate working vfork coverage for this port.

### Capacity and rename

Closed by source reading and host boundary checks. `P:195` requires string length including NUL plus three pointer widths in argspace, and length plus one pointer width in strspace. It charges one environment pointer once. Baseline, app and combined strings contain 51, 62 and 91 bytes including NUL. The argspace threshold rises by 11 or 40 bytes above baseline for app-only or combined insertion.

At one byte below the append threshold, the condition simply skips the append and returns success. The separate string-space condition and final alignment retain baseline slack. This does not cure pre-existing E2BIG during initial user-string copy or explicit sweetexecenv append.

`P:46` statically checks equal prefix widths. The denial memcpy at `P:148` overwrites the 22-byte name prefix only. The equals byte has the same value in both names. Value bytes, NUL, neighboring strings, counts and string offsets remain unchanged. The scan traverses extracted NUL-terminated strings and zero padding before `ip_endenvv`.
