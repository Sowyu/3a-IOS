# 2152 third audit

Verdict: NO-GO for an isolated test boot with sweetpwrfast=1 and sweetpanel=0 under the owner's stated requirements.

With sweetpwrfast=0, 2152 is acceptable for the isolated test kernel relative to the existing driver. I found no newly active display-control or frame-copy behavior in that configuration. This is a desk clearance of this patch, not a guarantee that existing scanout failure states are safe.

Reviewed on 2026-11-02. Patch SHA256 is d335e9bdf14a46379962bcdd0395492a5430a31ecbf580420e27f2424a3f6973, verified before and after checks. Source references below are relative to plans/input/work/p4 unless explicitly stated otherwise.

## Findings

### 1. A speculative transition can enter frozen scanout with black still displayed

Blocking. iokit/Kernel/arm/SweetFramebuffer.cpp:240, :272, :2495, :2533, :2540, :2594. iokit/Kernel/arm/SweetFbScale.h:158.

Concrete scenario: iOS remains on, the speculative black flip succeeds, then the expiry restore fails to latch and astFallback also fails to confirm the boot address. The hardware can keep scanning the last confirmed black slot. fastShowInBoot writes only slot 0, KEEP_WAIT retains the debt, and subsequent retries never issue another address change or modify that black slot. present and blackout both refuse to draw when frozen.

Keeping the debt fixes the bookkeeping loss from v2. It does not supply bounded visible recovery. The pre-existing frozen state does not exempt this case because 2152 introduces the speculative black and restore flips even when iOS does nothing and no new GPU frame exists. Those are new opportunities to enter the existing failure path, with a deliberately black last confirmed front. There is no measured probability increase, but the additional reachable transition is enough to reject an unconditional bound.

Proven by reading for the control flow. The hardware fault is inferred, not observed. I ran a scratch variant of the supplied model that lets failed fallback retain the last confirmed scanout instead of replacing visibility with UNKNOWN, and keeps iOS on through nine seconds. Fast power off had 0 ms darkness and did not freeze. Fast power on had 7899 ms darkness and retained debt at the end. This is a conditional fault simulation, not a phone measurement. Evidence is in analysis/2152-audit3-fault.log and its retained source.

The supplied frozen scenario checks debt_dropped only. The random walk explicitly exempts frozen runs from its darkness bound. Therefore its passing result does not clear the owner's requirement. This case blocks unless the requirement is explicitly narrowed or a visible recovery mechanism is provided.

### 2. A copy that exits early can destroy the only complete rollback image

Blocking. iokit/Kernel/arm/SweetFramebuffer.cpp:1459, :4381, :4391, :4440, :4453, :4454, :2491, :2545.

Concrete scenario: hardware scaling is on, black is on slot 2, and slot 1 is the only kept image. A multi-layer record copies its first ordinary layer into slot 1. A later layer refers to fSurface, the published default framebuffer surface. present then calls astFallback and returns immediately, before completing that frame. On the next fastRun, the stopped path ends darkness and fastRestore copies the partly composed slot 1 into boot scanout. With no further valid frame, that incomplete composition persists.

The default surface is exposed through the user-client API and the loop accepts multiple enabled layers. No preflight rejects this combination before earlier layers write the kept slot. The normal path would never flip that unfinished back buffer. The new recovery path explicitly uses it as the authoritative rollback image.

Proven by reading for the early return after earlier layer writes and the subsequent selection of that same slot. The triggering multi-layer record is a source-level counterexample, not a record observed on the phone. This violates the requested guarantee of restoring the old image or a complete newer frame, even without an actual latch fault.

Preserve a known complete image until a replacement presentation has finished successfully. At minimum, reject fallback-triggering records before any kept-slot write and preserve validity across every other aborted presentation. The work-loop gate and row-worker join prevent rollback from interrupting a healthy CPU copy halfway through, but do not undo an early return after earlier layers have written.

There is also no validity rollback when the final epoch check rejects a presentation after writing the kept slot. I ran a reduced C counterexample using the real sfs_fast_keep_next header, but its void-source contents are injected. That experiment proves only that the restore selector lacks validity state. It does not establish that GPU recovery corrupts an already completed, held source. The default-surface early-return case above is the basis for this blocker. The supplied regression model represents copies as atomic integer assignments and covers neither case.

### 3. Fallback recovery writes the buffer currently being scanned

Nonblocking for this isolated test, but transient tearing is expected to be possible. iokit/Kernel/arm/SweetFramebuffer.cpp:245, :2545, :4228, :4241, :4251.

Concrete scenario: restore fails, fallback successfully selects boot slot 0, then fastShowInBoot copies the kept image into that live scanout buffer. With hardware scaling it first clears the whole output to black and then draws scaled rows. A refresh can contain old black rows and restored image rows while the copy proceeds.

Proven by reading for the write-after-scanout-selection order. Actual tearing is inferred from asynchronous scanout and has not been measured. The work-loop gate and row-worker join prevent a concurrent normal CPU presentation or fast callback from modifying the same buffers during this function. They do not stop the display engine reading slot 0. dsb completes stores but does not make the whole image appear atomically.

This is a finite recovery artifact when copying and scanout continue, rather than persistent corrupt rollback. The ordinary fallback copy path already writes live boot memory, so this does not independently block the isolated boot. It would block a requirement forbidding even transient partial frames. The hardware-scale branch uses the same nearest-neighbour coordinate mapping as presentScaled, with ast.hwStride for the canvas and fRowBytes for output. It does not promise the QSEED filter's exact visual result.

### 4. The advertised recovery formula is conditional on work-loop and copy progress

Nonblocking as a separate finding. iokit/Kernel/arm/SweetFramebuffer.cpp:112, :2448, :2505, :2525, :4100, :4122.

Concrete scenario: the speculative deadline expires while present owns the gate and waits for a row helper. Both the event call and timeout call wait for that gate. There is no timed join of row workers and no independent watchdog that can restore visibility while the gate is held.

Proven by reading. No new lock cycle was found, and a delayed helper is not a demonstrated hardware failure. The usable bound is the configured window plus timer and gate scheduling delay, any in-progress presentation, flip and fallback waits, buffer seeding, recovery copy or scale, and scanout visibility delay. It is not a measured wall-clock upper limit.

The normal post-start astAddress waits are each capped at 25 ms. astFallback also seeds the boot buffer before its latch attempt, so the simplified formula omits that memory work and logging. No phone timing evidence establishes an upper bound for these costs. Finding 1 remains a stronger failure even when all software scheduling runs promptly.

### 5. New callback state still assumes permanent provider lifetime

Nonblocking for the built-in provider's isolated boot. iokit/Kernel/arm/SweetFramebuffer.cpp:352, :1239, :1245, :2448, :2560.

Concrete scenario: if AppleCLCD were freed or restarted after publication, a queued thread call or input producer could dereference the raw global pointer or its unretained callback parameter. There is no new stop/free path that withdraws publication, drains callbacks, or frees the simple lock. Partial allocation failure also leaks the successfully allocated pieces while keeping the feature disabled.

Proven by reading for missing teardown. I did not establish a reachable provider destruction path during this built-in test boot, so a use-after-free is inferred and does not independently block this scope. Provider restart or unload would need explicit lifetime management first.

## Claims that pass this desk review

The narrowing is implemented. The patch touches only sweet_keys.c, SweetHID.cpp, SweetFbScale.h, and SweetFramebuffer.cpp. It adds no panel-driver edit or DCS operation. fPanel is set from sweet_panel_mode before the boot-argument guard, so panel modes 1 and 2 disable fast power and log sweetpwrfast ignored. Missing asteroids flipping and zero-copy also disable it. The existing panel code still operates normally in those modes, but 2152 does not add speculative panel work.

With fast power off, the global event destination stays null, callback allocations are skipped, and fFast remains zero initialized. The no-flip and HUD conditions therefore preserve ordinary behavior. The power-generation increment and release/acquire stores still execute on power changes, and key/touch hooks make a null-return call. I found no new display operation from those changes.

Finding 4's ordinary non-frozen fallback path is repaired. fFastKept is set before attempting black, a failed black flip triggers immediate repayment in the same fastRun invocation, and a failed restore proceeds to the boot-buffer copy. The three-step loop covers FLIP, BOOT, DONE. KEEP_WAIT preserves the debt when frozen. No failed flip alone clears the debt. This passes the fault simulations, subject to findings 1 and 2.

Finding 6's speculative-window hold stall is repaired. While dark, vsyncFired still takes eligible pending or previous records and calls present with noflip set. Normal row workers finish before the 2120 sweet_hold_release point. The outer release covers early returns. The early swap callback stays suppressed, leaving tick consumption to release pending and sweetfb_keep records normally. No framebuffer-pixel retention now requires extending a CoreAnimation surface hold across the whole window.

The claim that every arriving frame is copied is too broad. Existing GPU gate, epoch, allocation, empty-swap and frozen checks can still reject work. For an eligible valid frame, dark-mode copying adds no second full-frame copy. It skips the ordinary partial-damage preservation copy and the flip wait. Compared with v2's early return it does restore the ordinary CPU copy or scale workload while black. The boot-buffer recovery copy or scale is additional failure-path work, not per-frame work. Cost has not been measured on the phone.

The event queue and generation design remains sound within the previously reviewed scope. Producers capture state before HID delivery, queue under a 16-entry simple lock, and release it before scheduling work. Draining releases that lock before acquiring fLock. RequestPowerChange stores state before generation, so a mixed snapshot cannot authorize a stale press against the later generation. Overflow cancels speculation, unsigned queue occupancy remains bounded across counter wrap, and the narrowed code adds no wake-panel state. I found no new lock-order cycle or event-order regression.
