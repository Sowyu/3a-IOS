## 1. The kept image survives aborted dark-mode presentations

Resolved for this test. Nonblocking. iokit/Kernel/arm/SweetFramebuffer.cpp:1488, :1491, :262, :4344, :4464, :4468, :4478, :4671.

Concrete scenario from audit 3: black is displayed, an ordinary layer copies successfully, and a later default-surface layer would call astFallback before the record completes. V4 preflights all enabled, nonzero surface IDs before the first destination write and refuses a record containing fSurface. The kept slot is untouched, and this presentation does not enter fallback. Refusal applies without hardware scaling too, which is deliberately more conservative than the old fallback condition.

Other dark-mode records compose through fDraw into fFastStage. Before the first preservation or layer write, fFastStageValid is cleared. A fresh partial record starts from the kept slot. A partial record following a complete staged frame preserves that staged frame's unchanged pixels. An incomplete previous attempt is discarded as a base and the next partial record starts from the kept slot again.

The row helpers join before the final epoch check. Only reaching astFlip after that check sets sweet_fb_stage_done, which the caller transfers into fFastStageValid. A late epoch rejection leaves the newly written stage invalid. Rollback then selects the intact kept image.

Proven by source control flow. The supplied model reproduces v3's default-surface and late-epoch counterexamples and reports zero incomplete-image exposure for v4. It also reports zero fallback entries from the default-surface record while dark. These are modeled records, not captured phone records.

The author's statement that every early return leaves the stage incomplete needs qualification. Returns before writing, including the preflight refusal and initial epoch rejection, can leave a previously complete stage valid. That is safe because those paths did not change its pixels. A completed frame means the ordinary compositor reached its commit point, not that every malformed layer necessarily drew pixels. Existing layer validation still skips unusable layers.

## 2. Copying the stage into the kept slot precedes scanning that slot

Passes within the existing latch-confirmation contract. Nonblocking. iokit/Kernel/arm/SweetFramebuffer.cpp:174, :278, :281, :290, :2519, :2528, :2532, :2570, :2585, :2588, :2593, :2636. iokit/Kernel/arm/SweetFbScale.h:140.

Concrete normal scenario: slot 1 is kept and the successful black flip confirms slot 2 as front. Dark-mode presentations never flip. On cancellation or expiry, SFS_KEEP_FLIP requires !ast.stopped and ast.front != kept. The stage copy therefore writes slot 1 while slot 2 remains the confirmed scanout. astFlip then issues the address change after its store barrier. A successful restore clears the debt on the next selector iteration.

A failed black flip always enters astFallback and sets ast.stopped before fastRestore runs. No dark-mode frame has staged anything between that flip and the immediate restore. Whether fallback confirms boot scanout or freezes with the old kept slot potentially still scanned, the selector chooses KEEP_BOOT, never KEEP_FLIP. There is no stage-to-kept memcpy on either path.

If the restore flip itself fails, the stage has already been copied safely into the kept slot. The next iteration sees stopped and copies that kept image into boot memory. If some other fallback stopped flipping while a complete stage remained valid, KEEP_BOOT selects the stage directly. Frozen retries enter KEEP_WAIT after that boot copy and never retry a kept-slot write.

Proven for software state transitions and serialization by the work-loop gate. An additional host check compiles the actual extracted fastRestore body and passes 16 combinations of stage validity, stopped state, frozen fallback, and restore-flip failure, plus both failed-black-flip outcomes. Physical scanout identity remains inferred from the driver's existing astAddress/astWait confirmation, not independently measured. A controller that falsely reports a completed latch remains outside that contract, as it was in v3.

## 3. The stage fits the planned canvas, but its capacity is not checked generally

Nonblocking for the planned isolated boot. Blocks clearance for arbitrary accepted canvas sizes. iokit/Kernel/arm/SweetFramebuffer.cpp:104, :453, :456, :925, :1251, :2281, :2287, :2588, :4480. plans/input/tools/build-input-loop.sh:17.

I parsed the ADT selected by the supplied image builder. Its canvas is 840x1860. With hardware scaling, the aligned stride is 3392 and the canvas occupies 6,309,120 bytes. The stage allocation is astBytes, 10,333,440 bytes or about 9.855 MiB, so this configuration fits. Without hardware scaling the destination uses the fixed 1080x2392 panel layout at stride 4320, exactly astBytes.

Concrete failure scenario outside that geometry: select a 1078x2390 canvas with stretch scaling and hardware scaling enabled. Both dimensions pass astSetup's smaller-than-panel checks, but the aligned stride is 4352 and the canvas is 10,401,280 bytes. A fresh partial dark-mode record's preservation memcpy writes 67,840 bytes past the stage allocation. A complete canvas copy or the later rollback read can also exceed its allocation. A 1079x2391 canvas exceeds it by 72,192 bytes.

Proven by source arithmetic and a runnable host counterexample. The existing physical flip-slot capacity also lacks this guard, but v4 introduces a separate undersized kernel heap allocation in that configuration. Heap corruption is inferred from executing those oversized accesses, not observed on hardware. A general release needs a capacity check or a correctly sized allocation. No patch was edited during this audit.

The allocation is made once at startup only when fast mode survives the panel, flip, and zero-copy guards. Its cost remains about 9.855 MiB even though the planned hardware canvas uses only about 6.017 MiB. Successful setup keeps it for the provider's lifetime. A complete staged rollback adds one full canvas or panel-buffer memcpy before the flip. Dark-mode partial composition can also need the initial kept-to-stage preservation copy. These costs have not been timed.

## 4. Accepted frozen-scanout limit remains reachable without a new failure transition

Accepted known limit. Nonblocking by the owner's decision. iokit/Kernel/arm/SweetFramebuffer.cpp:240, :278, :2577, :2591. iokit/Kernel/arm/SweetFbScale.h:148. plans/input/README.md:56.

Concrete scenario remains unchanged: black latched, the restore flip cannot be confirmed, and fallback cannot confirm boot scanout. The last confirmed black slot may remain visible while iOS is on. Boot-buffer copying and debt retention cannot force another address change in KEEP_WAIT.

Proven by source comparison: v4 retains the same flip, fallback, and debt-selector logic as v3. It adds no speculative address change or additional latch attempt. Default-surface preflight removes an existing way to enter fallback during darkness. The new stage memcpy adds CPU work before the restore attempt, but the latch timeout starts inside astFlip after that copy. I found no source-level change making this fault path more reachable. Equal hardware failure probability cannot be proven from desk work.

The README accurately says the panel can keep scanning black. The ponytail comment names the requested recovery trigger, the first phone log containing SWEET FB AST: fallback. Its wording that frozen scanout “leaves” black is stronger than the evidence. The failed fallback means scanout is unknown, so black is a possible outcome rather than the only one. The 91-run absence of that log is owner-supplied evidence, not independently re-counted here, and does not establish a failure rate.

## 5. Recovery avoids a second whole-buffer clear, but remains non-atomic

Improved. Nonblocking. iokit/Kernel/arm/SweetFramebuffer.cpp:225, :245, :4279, :4292, :4310, :4166. plans/input/README.md:54.

Concrete scenario: restore fails and fallback successfully puts boot memory on the panel. fastShowInBoot now clears only rows outside the scaled image and the left/right bars within its rows, then draws the image. It no longer explicitly blacks the image rectangle before drawing it. The planned geometry has zero bars, so this new bar-clear loop clears no image pixels.

Proven by reading the destination ranges. astFallback still seeds boot memory with black when hardware scaling is active, before selecting it. V4 therefore removes the additional full clear in fastShowInBoot, not every possible black interval. Copying or scaling into live boot scanout can still expose a partially restored refresh. Actual tearing and timing are inferred, not measured.

The recovery bound remains conditional on gate, timer, row-helper, memory-copy, and scanout progress. V4's documentation should also include the stage-to-kept memcpy before a restore flip when the stage is valid. In that failure case the work can include both that memcpy and a subsequent boot copy or scale. This omission affects the timing description, not the preserved-image guarantee.

## 6. Partial setup cleanup and off-mode clearance hold

Passes for the built-in provider's isolated lifetime. Nonblocking. iokit/Kernel/arm/SweetFramebuffer.cpp:1243, :1247, :1253, :1257, :1361, :1488, :2610, :4872.

Concrete allocation-failure scenario: the stage allocation fails after the simple lock and both thread calls succeed. V4 frees and nulls those pieces, leaves fFastMode zero, and never publishes sweet_fb_fast_fb. The same cleanup handles any subset of failed allocations. Publication follows complete success, so input producers cannot schedule the newly allocated calls during partial cleanup. Proven by source inspection. Allocation failures were not injected into a kernel.

With sweetpwrfast absent or zero, the allocation block is skipped, including the stage. The event destination remains null. The tick's fastRun call and power-change scheduling are guarded by fFastMode. fFast.dark remains false, so noflip remains false and the original destination and flip behavior remain selected. Default-surface preflight is short-circuited. V4 does still reset the small stage-done bookkeeping flag around ordinary presentations, and the pre-existing v3 input hooks and power-generation stores remain. “Nothing new runs” is therefore accurate for display and allocation behavior, not literally every instruction.

The former lifetime concern is unchanged for successful setup. There is no running-provider teardown that withdraws the raw global pointer, drains calls, and frees the stage and lock. If a provider were destroyed or restarted, stale callbacks could access it. Missing teardown is proven by reading. Reachable destruction during this built-in isolated boot was not established, so that failure scenario remains inferred and nonblocking for this scope.
